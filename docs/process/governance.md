# Governance

Settled 2026-04-25; contracts-check wording updated 2026-07-03 (`Decisions/2026-07-03-patterns-archive`).

## The three rules

1. **No auto-merge to `main`.** Feature PRs land through the merge train: open against the integration branch **`next`** (not `main`), get the mandatory independent reviewer pass, and Uni squash-merges each into `next` — one commit per PR, each properly marked Merged on GitHub. Nothing reaches `main` except through a single `next → main` PR, which **Aaron alone** merges, as a merge commit (never squash, so every constituent PR survives on `main` as its own commit) — except where merge authority is explicitly delegated (currently only `parachute-brain`). This is enforced mechanically, not just by convention: branch protection restricts pushes/merges on `main` to Aaron; Uni's write access only ever lands on `next`, which is itself unprotected — a disposable integration branch, never force-pushed or deleted. All core repos have branch protection on `main` (PR-required, no force-push, no deletion). Required-review-count is 0 while solo-team; bumps to ≥1 when a second human contributor joins. A branch-protection "bypass" warning is not authorization.

   **Why this changed (2026-08-14).** Per-PR clicks on `main` didn't scale with throughput. Aaron's call: "fewer merges... each PR its own commit... still have ultimate say" — the train gives him one click per coherent batch instead of one per PR, while every PR still lands as its own reviewable, revertable commit.
2. **Version bumps live in the batch release PR, not feature PRs.** Feature PRs carry code + tests, land on `next`, and **do not touch `package.json` version or `CHANGELOG.md`** — `release-check.sh` checks this locally before you open. The bump happens once per batch, in the same PR that lands the batch on `main`: Uni cuts the `next → main` PR with a final commit that bumps the version and writes the changelog covering everything merged since the last release; Aaron's single merge-commit click (rule 1) lands the batch **and** publishes the release in one motion — merging it publishes (see below). Pre-1.0 that bump is the `rc.N` suffix only, keeping `0.X.Y` fixed across the chain; when Aaron says ready-for-release, drop the `-rc` suffix at the same `0.X.Y` to publish `@latest`. Sync the lockfile with every version bump (frozen-lockfile is CI-only). Know the repo's convention — parachute-surface ships stable patch bumps, not rc.

   **Why this changed.** *2026-07-29 — stopped bumping per PR.* Every PR used to bump the version and prepend to the changelog, so with N PRs open against one repo, each merge conflicted the other N−1 — on the same two lines, every time. One session burned six rebases on nothing but version numbers and changelog headers. Worse, resolving those conflicts silently *dropped* two merged changelog entries, because a `str.replace` anchored on a header that didn't exist is a no-op that fails nothing. Shared-line edits in every PR is the whole cause; removing them removes the class. *2026-08-10 — bundled became the standing cadence.* Aaron: never per-PR again — accumulate merged work and cut one release per coherent set, not one per feature. *2026-08-14 — folded into the merge train.* Cutting the release is no longer a separate act from landing a batch: it's the final commit of the `next → main` PR (rule 1), so one Aaron click does both.

   **Deploying is not a reason to promote.** If a box needs a merged fix, cut an **rc** and point the box at `@rc` — never promote to stable to get code onto a machine. On 2026-07-30 four stable releases shipped in one evening for exactly that reason (the box needing each fix tracked `@latest`, so promoting was the only way to reach it), and one of them put a front door that couldn't render on `@latest` for every new install. Stable is a judgement that a train is good, not a delivery mechanism. Set a box's channel with the persisted `module_install_channel` setting (admin SPA, or `PARACHUTE_INSTALL_CHANNEL`), not a one-off install — a raw `bun add -g <pkg>@rc` leaves the setting untouched, so the next `parachute install` silently pulls stable again and the box ends up on mixed channels.

   **`@rc` can be BEHIND `@latest` — check before pointing a box at it.** When trains ship stable-direct without cutting rcs, the rc dist-tag goes stale and `bun add -g <pkg>@rc` becomes a **downgrade**. Hit live on 2026-07-30: moving a box to rc took hub `0.7.11` → `0.7.9-rc.6` and reinstated a bug fixed two releases earlier. `parachute upgrade` survives this (best-of resolution across rc/latest, hub#659); a raw `bun add -g` does not, and neither does any script pinning `@rc`. Cut an rc that is *ahead* of stable before moving anything onto the channel.

   **Publishing is on merge, not on a remembered tag.** CI compares `package.json`'s version against npm and publishes when it's new — idempotent, refuses on an ambiguous registry, and refuses to move a dist-tag backwards. So the release PR *is* the release signal, and there is no tag to forget. (Tag pushes still work and still override, for re-releases.) A dist-tag is derived from the version being published, never from the git ref — deriving it from `GITHUB_REF_NAME` sends every merge-triggered publish to `@latest`, which is how an rc briefly became `@latest`.

   **Stack related PRs** that depend on each other rather than opening them all against `next` independently: branch each off the previous one. Independent work can go parallel safely now that feature PRs share no lines.
3. **Contracts check in every review.** Each PR review surfaces which cross-repo contracts the change touches (wire shapes, OAuth issuer behavior, portable-md format, module protocol) and whether it conforms. Contract docs live with the repo that enforces them (migrating there as parachute-patterns archives); the specialist briefs in `.claude/skills/review-subagents/` encode the load-bearing ones.

## PR flow

- **Concurrent when disjoint, bundled within**: feature PRs target `next`, not `main` (rule 1); concurrent PRs per repo are fine when they don't collide (see `orchestration.md` for the test); one PR per coherent session of work (multiple commits fine). Side-discoveries → `gh issue create` rather than widening the PR.
- **Reviewer nits relevant to the diff fold inline** (same PR, same rc); out-of-scope findings become issues.
- **Verified-conditional merge**: after `gh pr merge` (into `next`, or Aaron's `next → main`), confirm `state == MERGED` before any hygiene (reset/force-push of the dev branch) — transient merge failures + unconditional hygiene have clobbered open PRs before.
- **Never merge on a red/UNSTABLE gate without reading it.** Don't assume a red gate is pre-existing.
- **External PRs** require Aaron's identity-verified approval — never merge outside-contributor code on code-scope alone.

## npm publishes

CI's job (OIDC trusted publishing — no tokens), triggered on merge to `main`: it compares `package.json`'s version against npm and publishes when it's new (rule 2). A `v*` tag push still works and still overrides, for re-releases — but the batch release PR landing is the normal release signal, not a tag. After publishing, verify: `npm view <pkg>@<version> dist.tarball`. Watch for bun's stale-manifest cache on deploy boxes (`rm -rf ~/.bun/install/cache` if a fresh version won't resolve).

## Architectural shifts → migration files

When a PR decides an architectural shift — canonical install path, a doc statement quoted across the workspace, a repo's role — ship a migration checklist file in the same PR listing every code/doc location that needs updating, and track which PRs landed each item. (Historically these lived in `parachute-patterns/migrations/`; as that repo archives, new ones land in the destination decided by the coherence program — check `Work/repo-coherence-program` in the team vault.) Run an audit for stale canonical references after shifts and before releases.
